# Publish gate (P0) — how a package becomes a published article here

Owner: Suho. Enforced by: the project's own gate, in the live publish path.

## What runs, and where

`npm run gate` is the single sanctioned publish/validation entry point:

```text
npm run gate            -> node scripts/seo-gates.mjs && node scripts/publish-gate.mjs
npm run build           -> npm run gate && node build.mjs
npm run build:vercel    -> npm run gate && node build.mjs && bake/base/markdown/stage
```

`vercel.json` sets `"buildCommand": "npm run build:vercel"`, and
`.github/workflows/seo.yml` runs `npm run build`. Both therefore execute the
publish gate before anything can ship. A failing gate exits `1`, so the build
stops and nothing is deployed.

## The order that cannot be reversed

`scripts/publish-gate.mjs` calls the deterministic validator BEFORE it writes
anything:

```bash
python3 seo/validate_publish_package.py --package <pkg.json> --publish-root <dir>
```

- exit `0` → the package may publish;
- any non-zero exit → that package publishes **nothing**: no file, no directory,
  no staging residue, and the run exits `1` so the build stops.

Only after exit `0` does the publisher write, and it writes exactly once: a
fully-built staging directory is moved into place with a single `rename(2)`
inside the publish root (same filesystem, so the move is atomic). A reader sees
either the old state or the complete article, never a half-written one. The
package record travels inside the published directory, so the audit trail and
the page land together or not at all. An existing destination is refused — a
slug is never overwritten.

The `human_signoff: {name, datetime, scope}` P0 gate and the scale gate
(`body_words < 320` → `noindex: true`) are enforced by the validator, not by
this script. Neither an AI nor a cronjob may sign on a human's behalf.

## Paths and overrides

| Purpose | Default | Override |
|---|---|---|
| Publish root | `shared/blog` | `PUBLISH_ROOT` |
| Package inbox | `shared/publish-inbox` | `PUBLISH_INBOX` |
| Validator | `seo/validate_publish_package.py` | `PUBLISH_VALIDATOR` |
| Python | `python3` | `PUBLISH_PYTHON` |

An explicit package can be published with
`node scripts/publish-gate.mjs --package <path.json>`.

No packages in the inbox is a silent no-op that never invokes python, so an
ordinary code deploy does not depend on this gate.

Publisher-side rule (stricter than the validator, which is the minimum bar):
`published_path` must be exactly `<slug>/index.html`, because the whole article
directory then publishes in one atomic rename.

## Tests

```bash
node --test test/publish-gate.test.js
```

Covers the P0 acceptance path directly: an unsigned package is refused and the
publish root stays empty; a thin body is refused; a signed package publishes
atomically with its record; an existing destination is refused byte-identical;
a bad package beside a good one does not stop the good one from shipping.

## Not part of this gate

Sitemap, RSS, and the blog index are generated by `node build.mjs` from
`data/blog-articles.json`. Registering a published article in that registry
(and honouring `noindex: true` by excluding it) stays a build/registry concern;
this gate decides only whether a package may be written to the publish root.
